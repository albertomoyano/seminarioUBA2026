# GitHub para participantes de un repositorio

## Introducción

Este documento está pensado para estudiantes y participantes de un repositorio en GitHub que **no necesariamente tienen conocimientos de programación**.

La idea es explicar de manera simple cómo participar correctamente dentro de un repositorio ya existente.

Importante:
En este caso ustedes **no son quienes administran el repositorio**. Es decir, no necesitan tomar decisiones técnicas ni gestionar el proyecto. Su rol es participar, consultar, informar problemas y seguir las actividades propuestas.

Pueden pensar GitHub como un espacio de trabajo compartido donde:

- se publica información,
- se organizan tareas,
- se hacen consultas,
- se reportan problemas,
- y se mantiene comunicación ordenada entre participantes.

---

# ¿Qué es un repositorio?

Un repositorio es el espacio principal del proyecto.

Allí pueden encontrar:

- documentos,
- materiales,
- publicaciones,
- enlaces,
- actividades,
- archivos,
- discusiones,
- y seguimiento de problemas o tareas.

No hace falta entender programación para utilizarlo.

---

# Qué deben mirar primero

Cuando ingresan a un repositorio, normalmente lo más importante para ustedes será:

- `README`
- `Discussions`
- `Issues`
- notificaciones

---

# README

El archivo `README` suele ser la portada del proyecto.

Ahí generalmente encontrarán:

- explicación general,
- instrucciones,
- enlaces importantes,
- normas de participación,
- materiales,
- cronogramas,
- y formas de comunicación.

Siempre conviene leerlo primero.

---

# Discussions

## ¿Qué son?

Las **Discussions** son espacios de conversación.

Sirven para:

- hacer preguntas,
- intercambiar ideas,
- responder actividades,
- compartir avances,
- comentar materiales,
- y mantener conversaciones grupales.

Piensen las Discussions como un foro organizado.

---

## Cuándo usar una Discussion

Usen una Discussion cuando:

- tienen una duda general,
- quieren comentar una actividad,
- desean compartir una reflexión,
- necesitan hacer una consulta no urgente,
- quieren participar en una conversación grupal.

---

## Ejemplos

### Correcto

- “No entendí la consigna del ejercicio 3”
- “Comparto mi reflexión sobre el texto”
- “¿Alguien pudo instalar el programa?”
- “Encontré este recurso relacionado”

### Incorrecto

- Reportar un error técnico específico del repositorio.
- Informar que un enlace está roto.
- Avisar que un archivo importante falta.

En esos casos corresponde usar un **Issue**.

---

# Issues

## ¿Qué son?

Los **Issues** sirven para reportar problemas concretos o situaciones que requieren corrección o seguimiento.

No son conversaciones generales.

Piensen un Issue como un “aviso formal” sobre algo que necesita atención.

---

## Cuándo usar un Issue

Usen un Issue cuando encuentren:

- errores,
- enlaces rotos,
- archivos faltantes,
- problemas técnicos,
- información incorrecta,
- fallos en instrucciones,
- dificultades reproducibles.

---

## Ejemplos

### Correcto

- “El PDF de la unidad 2 no abre”
- “El enlace de descarga está roto”
- “La fecha publicada en el cronograma parece incorrecta”
- “No aparece el archivo mencionado en la guía”

### Incorrecto

- “¿Qué opinan del texto?”
- “No entendí una consigna”
- “¿Alguien más está estudiando esto?”

Eso corresponde a una Discussion.

---

# Diferencia rápida entre Discussions e Issues

| Situación | ¿Discussion o Issue? |
|---|---|
| Hacer una pregunta | Discussion |
| Conversar sobre un tema | Discussion |
| Compartir una reflexión | Discussion |
| Reportar un error | Issue |
| Avisar que falta un archivo | Issue |
| Informar un problema técnico | Issue |

---

# Notificaciones

GitHub puede enviar notificaciones cuando hay actividad.

Esto es importante para seguir el curso o las actividades del repositorio.

---

# Watch y Subscribe

## Watch

La opción **Watch** sigue todo el repositorio para primera comunicación.

Puede incluir:

- Discussions,
- Issues,
- anuncios,
- cambios generales.

Es útil si quieren mantenerse al tanto de toda la actividad.

---

## Subscribe

La opción **Subscribe** sigue de manera persistente solamente una publicación específica.

Por ejemplo:

- una Discussion,
- un Issue.

Es la forma más práctica de seguir conversaciones importantes.

---

# Algo importante sobre las notificaciones

GitHub también los suscribe automáticamente cuando:

- hacen un comentario,
- responden en una Discussion,
- participan en un Issue.

Por eso, a veces reciben notificaciones aunque nunca hayan usado el botón “Subscribe”.

Esto es normal.

---

# Buenas prácticas de participación

## Antes de preguntar

Revisen si:

- la respuesta ya está en el README,
- existe una Discussion similar,
- alguien ya hizo la misma consulta.

---

## Escriban títulos claros

En lugar de:

- “Ayuda”
- “Tengo un problema”

Es mejor:

- “No puedo abrir el PDF de la unidad 3”
- “Duda sobre la actividad práctica”

---

## Mantengan el tema de cada publicación

Si una Discussion habla sobre una actividad específica, intenten no cambiar el tema.

Esto ayuda a mantener el repositorio organizado.

---

## Sean claros y respetuosos

No hace falta usar lenguaje técnico.

Lo importante es:

- explicar bien el problema,
- describir qué ocurrió,
- y escribir de manera clara.

---

# No tengan miedo de participar

GitHub puede parecer complejo al principio, especialmente para quienes no vienen del área de programación.

Pero para participar en un repositorio educativo normalmente solo necesitan:

- leer,
- comentar,
- responder,
- abrir Discussions,
- y eventualmente crear Issues simples.

Con el uso cotidiano, la plataforma se vuelve mucho más natural.
